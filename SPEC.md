# Технічне завдання
## Симулятор взаємодії BESS ↔ EMS на ринку електроенергії України

Версія 1.0 · 2026-09-06

---

## 1. Мета проекту

Розробити програмний комплекс, який **імітує реальну взаємодію** системи накопичення енергії (BESS — Battery Energy Storage System) з системою керування енергією підприємства (EMS — Energy Management System) в умовах українського ринку електроенергії.

Комплекс має:
1. Симулювати фізичну поведінку батареї (заряд/розряд, SoC, втрати, деградація).
2. Збирати історичні та поточні дані: споживання підприємства, погодинні ціни РДН, стан батареї.
3. За допомогою ML/DL прогнозувати ціни та споживання на наступну добу.
4. Оптимізувати графік заряду/розряду для максимізації прибутку (арбітраж) та/або економії (зрізання піків, самоспоживання).
5. Надавати веб-застосунок для керування, налаштування та **дашборд у реальному часі з анімованою схемою потоків енергії** (стрілки, батарея, що заповнюється, лічильники грошей).

Кінцевий результат — навчально-демонстраційна платформа, максимально наближена до реальної архітектури промислових BESS/EMS-рішень (реальні протоколи, реальні структури даних, реальна логіка ринку), але повністю автономна (без підключення до реального обладнання).

## 2. Глосарій

| Термін | Пояснення |
|---|---|
| **BESS** | Battery Energy Storage System — батарея + інвертор (PCS) + BMS |
| **EMS** | Energy Management System — «мозок», приймає рішення що і коли робити |
| **BMS** | Battery Management System — контролер батареї, віддає SoC, SoH, напругу, температуру |
| **PCS** | Power Conversion System — інвертор, задає активну потужність заряду/розряду |
| **SoC** | State of Charge — рівень заряду, 0–100 % |
| **SoH** | State of Health — стан здоров'я батареї, деградація ємності |
| **C-rate** | Відношення потужності до ємності (1C = повний заряд за 1 годину) |
| **РДН** | Ринок «на добу наперед» (Day-Ahead Market, DAM) — торги погодинними лотами на наступну добу |
| **ВДР** | Внутрішньодобовий ринок (Intraday) |
| **БР** | Балансуючий ринок |
| **ОЕС** | Об'єднана енергосистема України |
| **Setpoint** | Команда EMS → BESS: цільова потужність (кВт), знак = напрямок |
| **Dispatch** | Виконання графіка — видача setpoint'ів у реальному часі |
| **Арбітраж** | Купити дешево вночі → продати/використати дорого у пік |
| **Peak shaving** | Зрізання пікового споживання підприємства з мережі за рахунок батареї |

## 3. Ринковий контекст (Україна) — що має бути змодельовано

Симулятор має відтворювати правила, які реально діють для непобутового споживача з власним накопичувачем:

### 3.1. Структура ціни для підприємства
Ціна купівлі 1 кВт·год = **ціна РДН(година)** + тариф на передачу (Укренерго) + тариф на розподіл (обленерго, за класом напруги) + послуги постачальника.
Ціна продажу надлишку в мережу = **ціна РДН(година)** × коефіцієнт (за замовчуванням 0.9 — можна налаштувати) або фіксована ціна за договором.

Усі складові — параметри, які задаються в налаштуваннях (грн/МВт·год). Значення за замовчуванням задати як «правдоподібні на 2025–2026 рік» і чітко позначити як демонстраційні.

### 3.2. Ринок «на добу наперед» (РДН)
- Торги закриваються **до 12:00** дня D на добу D+1.
- 24 погодинні ціни на добу D+1 публікуються після ~13:00 дня D.
- Отже EMS має **о 11:00 дня D** сформувати прогноз цін і споживання на D+1 і побудувати попередній графік. Після публікації фактичних цін РДН о 13:00 — перерахувати графік з фактичними цінами (прогноз використовується лише там, де факту ще немає, — споживання, ВДР).
- Є price cap (мінімальна/максимальна дозволена ціна по годинах) — налаштовуваний параметр.

### 3.3. Типовий добовий профіль цін ОЕС
Генератор синтетичних даних має відтворювати характерну форму: низька ціна 00:00–06:00, ранковий підйом 07:00–11:00, денний спад 12:00–16:00, вечірній пік 17:00–23:00 (найдорожчий 19:00–22:00), сезонність (зима дорожча), день тижня (вихідні дешевші), випадкові стрибки (шоки).

### 3.4. Джерела реальних даних (опціонально)
Передбачити імпорт CSV з реальними погодинними цінами РДН (формат: `date, hour, price_uah_mwh, zone`). Джерело — публічні дані ДП «Оператор ринку». Якщо файлу немає — працює синтетичний генератор.

Усе піднімається одним `docker compose up`.

### 4.2. Принципи
- **BESS і EMS — окремі процеси**, спілкуються лише через MQTT. Це критично: BESS не знає нічого про ринок, EMS не має прямого доступу до внутрішнього стану батареї — лише те, що BMS публікує в телеметрії.
- **Єдиний симуляційний час.** EMS володіє годинником (`SimulationClock`). Швидкість налаштовується: `1x` (реальний час), `60x` (1 хв = 1 год), `3600x`, `pause`, `step`. BESS отримує поточний сим-час у кожному повідомленні і симулює фізику за `Δt`.
- **Детермінованість.** Заданий `seed` → однаковий результат симуляції (для тестів і порівняння стратегій).
- **Все конфігурується з UI**, без правки коду.

### 4.3. Протокол обміну (MQTT, JSON)

Топіки:

| Топік | Напрямок | Періодичність |
|---|---|---|
| `bess/{id}/telemetry` | BESS → EMS | кожен сим-тік (за замовч. 1 сим-хвилина) |
| `bess/{id}/status` | BESS → EMS | при зміні стану / раз на сим-хвилину |
| `bess/{id}/alarm` | BESS → EMS | подія |
| `ems/{id}/setpoint` | EMS → BESS | при зміні команди |
| `ems/{id}/command` | EMS → BESS | start / stop / standby / reset_alarm |
| `sim/clock` | EMS → всі | кожен сим-тік |

**Телеметрія BESS** (`bess/{id}/telemetry`):
```json
{
  "ts_sim": "2026-03-14T18:00:00Z",
  "ts_wall": "2026-09-06T14:22:31.120Z",
  "bess_id": "bess-01",
  "soc_pct": 63.4,
  "soh_pct": 98.7,
  "soe_kwh": 634.0,
  "power_kw": -180.0,
  "voltage_v": 782.4,
  "current_a": -230.1,
  "temp_c": 31.2,
  "cycles_total": 412.5,
  "throughput_kwh": 825000,
  "state": "DISCHARGING",
  "available_charge_kw": 250,
  "available_discharge_kw": 250,
  "alarms": []
}
```
Конвенція знака: `power_kw < 0` — розряд (віддає в об'єкт/мережу), `> 0` — заряд.

**Setpoint EMS → BESS** (`ems/{id}/setpoint`):
```json
{
  "ts_sim": "2026-03-14T18:00:00Z",
  "setpoint_kw": -180.0,
  "mode": "P_CONST",
  "valid_until_sim": "2026-03-14T19:00:00Z",
  "reason": "SCHEDULE_DISCHARGE_ARBITRAGE",
  "schedule_id": "sch_20260314_v2"
}
```

**Стан BESS** (кінцевий автомат): `OFFLINE → STANDBY → CHARGING | DISCHARGING | IDLE → FAULT`.
Переходи в `FAULT` при: перегрів (> `temp_max`), SoC поза жорсткими межами, перевищення потужності. З `FAULT` вихід лише командою `reset_alarm`.

Опціонально (етап 6): додатково віддавати той самий стан через **Modbus TCP** (pymodbus) з картою регістрів у стилі SunSpec — для максимального реалізму. Не обов'язково для MVP.

## 5. BESS Simulator — детальні вимоги

Окремий Python-сервіс `bess-sim/`.

### 5.1. Параметри батареї (конфіг, змінюються з UI)
| Параметр | Default | Опис |
|---|---|---|
| `capacity_kwh` | 1000 | Номінальна ємність |
| `power_max_kw` | 500 | Макс. потужність заряду і розряду (0.5C) |
| `soc_min_pct` / `soc_max_pct` | 10 / 90 | Робочі межі |
| `soc_hard_min` / `soc_hard_max` | 5 / 97 | Аварійні межі → FAULT |
| `eff_charge` / `eff_discharge` | 0.95 / 0.95 | ККД (round-trip ≈ 0.90) |
| `self_discharge_pct_day` | 0.1 | Саморозряд |
| `aux_load_kw` | 3.0 | Власні потреби (HVAC, контролери) |
| `ramp_rate_kw_s` | 50 | Обмеження швидкості зміни потужності |
| `temp_ambient_c` | 25 | Зовнішня температура |
| `temp_max_c` | 45 | Поріг перегріву |
| `degradation_model` | `cycle_linear` | Модель деградації |
| `cycle_life` | 6000 | Циклів до 80 % SoH |
| `capex_uah` | 15 000 000 | Для розрахунку вартості деградації |
| `initial_soc_pct` | 50 | Стартовий SoC |

### 5.2. Фізична модель (на кожен тік `Δt`)
1. Прийняти `setpoint_kw`, обрізати по `available_charge_kw` / `available_discharge_kw` (залежать від SoC — біля меж потужність знижується лінійно, як у реальних BMS: при SoC > 85 % заряд обмежується) і по `ramp_rate`.
2. Заряд: `ΔE = P · Δt · eff_charge`; розряд: `ΔE = −P · Δt / eff_discharge`.
3. `SoE += ΔE − self_discharge − aux_load·Δt`; `SoC = SoE / capacity_actual`.
4. Тепло: спрощена модель `dT/dt = (P²·R_internal − k·(T − T_ambient)) / C_thermal`.
5. Деградація: `cycles_total += |ΔE| / (2 · capacity)`; `capacity_actual = capacity · (1 − 0.2 · cycles_total / cycle_life)`; `SoH = capacity_actual / capacity`.
6. Напруга/струм — синтетика від SoC (OCV-крива для LFP, табличка 10 точок) і потужності.
7. Перевірити аларми → можливий перехід у FAULT.
8. Опублікувати телеметрію.

### 5.3. Внесення несправностей (для реалізму та тестування EMS)
З UI можна увімкнути: випадковий дропаут зв'язку (не публікувати телеметрію N сим-хвилин), шум у SoC (±0.5 %), примусовий перегрів, обмеження потужності на 50 %. EMS має коректно це обробляти (див. 6.5).

## 6. EMS Core — детальні вимоги

Сервіс `ems/` (FastAPI + asyncio). Модулі:

### 6.1. Ingestion (збір даних)
- Підписка на MQTT-телеметрію → запис у TimescaleDB (`bess_telemetry`).
- Імпорт CSV: споживання підприємства (`ts, load_kw`), ціни РДН (`date, hour, price`), опційно генерація PV (`ts, pv_kw`), погода (`ts, temp, cloud, wind`).
- Синтетичний генератор для кожного ряду з параметрами (сезонність, шум, seed). Профіль споживання: типовий для виробничого підприємства (пн–пт 07:00–19:00 високе, нічний мінімум, вихідні ~30 %). Мінімум **2 роки** історії для тренування.
- Валідація, ресемплінг до 1 години і до 15 хвилин, заповнення пропусків.

### 6.2. Market Simulator
- Веде «поточну добу» в сим-часі; о 13:00 сим-дня публікує фактичні ціни РДН на D+1 (з CSV або генератора).
- Рахує повну ціну купівлі/продажу за формулою з розділу 3.1.
- Рахує фінансовий результат кожної години: `cost_without_bess`, `cost_with_bess`, `revenue_export`, `savings`, `degradation_cost`, `net_profit`. Накопичує по добі/місяцю.

### 6.3. Forecaster (ML/DL) — детально в розділі 8
Дві задачі: прогноз ціни РДН на 24 год і прогноз навантаження підприємства на 24 год (крок 1 год, опційно 15 хв). Запуск за розкладом (11:00 сим-дня) або вручну з UI.

### 6.4. Optimizer — детально в розділі 9
Вхід: прогнози/факти на горизонт 24–48 год, стан BESS, параметри стратегії. Вихід: погодинний графік `schedule[t] = {p_kw, action, expected_soc, expected_profit}`.

### 6.5. Dispatcher (реальний час)
- Кожен сим-тік читає поточний графік, формує setpoint і публікує в MQTT.
- **Замкнене керування:** якщо фактичний SoC відхиляється від планового > `soc_tolerance` (3 %) — тригер ре-оптимізації на решту горизонту (rolling horizon).
- Реактивні правила пріоритетніші за графік: (а) SoC ≤ soc_min → заборонити розряд; (б) peak-shaving: якщо `load − p_dis > peak_limit_kw` — підняти розряд до дозволеного; (в) якщо BESS у FAULT або немає телеметрії > 3 сим-хв → перейти в `SAFE_MODE`, setpoint = 0, підняти аларм у UI.
- Логує кожне рішення з причиною (`reason`) — для пояснюваності на дашборді.

### 6.6. Simulation Clock
- `speed ∈ {0 (pause), 1, 10, 60, 600, 3600}`, `step()`, `jump_to(datetime)`, `reset(scenario)`.
- Тік = 1 сим-хвилина. Публікує `sim/clock`.
- Сценарії: «Зимовий тиждень», «Літній місяць», «Рік 2025», «Кастом» (обрати початок/кінець з наявних даних).

### 6.7. Стратегії (обираються в UI, можна комбінувати вагами)
| Стратегія | Мета |
|---|---|
| `ARBITRAGE` | Купити дешево / продати дорого, максимізувати прибуток |
| `PEAK_SHAVING` | Не перевищувати `peak_limit_kw` імпорту з мережі (економія на потужності / штрафах) |
| `SELF_CONSUMPTION` | Максимально накопичувати надлишок PV, мінімізувати імпорт |
| `TOU_SIMPLE` | Правило без ML: заряд у «дешеві» години, розряд у «дорогі» (baseline для порівняння) |
| `BACKUP_RESERVE` | Завжди тримати `reserve_soc_pct` на випадок відключення |

## 7. Дані та схема БД

PostgreSQL 16 + TimescaleDB. Усі часові таблиці — hypertable по `ts`.

```sql
-- Телеметрія батареї (сирі дані з MQTT)
CREATE TABLE bess_telemetry (
  ts TIMESTAMPTZ NOT NULL, bess_id TEXT NOT NULL,
  soc_pct REAL, soh_pct REAL, soe_kwh REAL, power_kw REAL,
  voltage_v REAL, current_a REAL, temp_c REAL, state TEXT, alarms JSONB
);

-- Навантаження підприємства (факт)
CREATE TABLE site_load (ts TIMESTAMPTZ NOT NULL, load_kw REAL, pv_kw REAL DEFAULT 0, source TEXT);

-- Ціни РДН
CREATE TABLE dam_prices (
  ts TIMESTAMPTZ NOT NULL, zone TEXT DEFAULT 'OES',
  price_uah_mwh REAL, published_at TIMESTAMPTZ, source TEXT
);

-- Прогнози (зберігаємо всі версії для оцінки якості)
CREATE TABLE forecasts (
  id BIGSERIAL, created_at_sim TIMESTAMPTZ, target TEXT, -- 'price' | 'load'
  model_name TEXT, model_version TEXT, horizon_h INT,
  ts TIMESTAMPTZ, value REAL, p10 REAL, p90 REAL
);

-- Графіки оптимізації
CREATE TABLE schedules (
  id TEXT PRIMARY KEY, created_at_sim TIMESTAMPTZ, strategy JSONB,
  horizon_start TIMESTAMPTZ, horizon_end TIMESTAMPTZ,
  expected_profit_uah REAL, solver_status TEXT, solve_time_ms INT, items JSONB
);

-- Рішення диспетчера (пояснюваність)
CREATE TABLE dispatch_log (
  ts TIMESTAMPTZ NOT NULL, setpoint_kw REAL, actual_kw REAL,
  reason TEXT, schedule_id TEXT, override BOOLEAN
);

-- Погодинні фінансові результати
CREATE TABLE financials (
  ts TIMESTAMPTZ NOT NULL, import_kwh REAL, export_kwh REAL,
  price_buy REAL, price_sell REAL, cost_baseline_uah REAL,
  cost_actual_uah REAL, revenue_uah REAL, degradation_uah REAL, net_uah REAL
);

CREATE TABLE settings (key TEXT PRIMARY KEY, value JSONB, updated_at TIMESTAMPTZ);
CREATE TABLE ml_models (name TEXT, version TEXT, target TEXT, trained_at TIMESTAMPTZ,
  metrics JSONB, artifact_path TEXT, is_active BOOLEAN, PRIMARY KEY(name, version));
```

Формати CSV для імпорту — задокументувати в `docs/data-formats.md`, покласти приклади в `data/samples/`.

## 8. ML / DL — прогнозування

### 8.1. Задачі
| Ціль | Горизонт | Крок | Метрики |
|---|---|---|---|
| Ціна РДН | 24 год (D+1), опційно 48 | 1 год | MAE, MAPE, RMSE, **rank correlation** (важливо для арбітражу — порядок годин важливіший за абсолют) |
| Навантаження | 24 год | 1 год / 15 хв | MAE, MAPE, RMSE, peak-hour error |

### 8.2. Фічі
- Календарні: година, день тижня, місяць, день року (sin/cos), вихідний/свято (український календар свят — таблиця у конфізі), опалювальний сезон.
- Лаги: значення на ту саму годину 1, 2, 7, 14 днів тому; ковзні середні 24h/168h; мін/макс останньої доби.
- Для ціни: лаги навантаження ОЕС (синтетичне), погода (температура, хмарність, вітер — синтетика або CSV), «шоки» (індикатор).
- Для навантаження: виробничий календар підприємства (змінність), температура.

### 8.3. Моделі (реалізувати всі три рівні, порівняти)
1. **Baseline:** naive (те саме, що вчора / тиждень тому), seasonal naive.
2. **Класичний ML:** LightGBM (multi-output або 24 моделі по горизонту), із quantile-режимом для p10/p90.
3. **DL:** LSTM/GRU seq2seq або TCN у PyTorch; вхід — 168 год історії + майбутні відомі фічі (календар, погодний прогноз); вихід — 24 значення. Опційно — Temporal Fusion Transformer через `pytorch-forecasting`.

### 8.4. Пайплайн
- `ems/ml/train.py --target price --model lightgbm --from 2024-01-01 --to 2025-12-31`
- Walk-forward валідація (розширювальне вікно, крок 1 місяць).
- Артефакти зберігаються в `models/{target}/{model}/{version}/` (pickle / `.pt` + `metadata.json` з метриками).
- Активна модель обирається в UI; можливо запустити перетренування з UI (фоновий task, прогрес по WebSocket).
- Сторінка порівняння: таблиця метрик усіх моделей + графік «прогноз vs факт» за обраний період + **backtest прибутку**: скільки б заробив оптимізатор з кожним прогнозом проти ідеального (perfect foresight).

### 8.5. Онлайн-режим
У сим-часі щодня о 11:00 forecaster робить прогноз активною моделлю на D+1, зберігає у `forecasts`. Після публікації факту РДН (13:00) EMS рахує помилку і показує на дашборді «якість прогнозу за останні 7 днів».

## 9. Оптимізація графіка (MILP)

Розв'язувач: **PuLP + CBC** (або OR-Tools). Горизонт `T` = 24–48 год, крок 1 год (параметр).

### 9.1. Змінні (для кожної години `t`)
- `p_ch[t] ≥ 0`, `p_dis[t] ≥ 0` — потужність заряду/розряду, кВт
- `z[t] ∈ {0,1}` — 1 = заряд, 0 = розряд (заборона одночасного)
- `soc[t]` — енергія в батареї, кВт·год
- `g_imp[t] ≥ 0`, `g_exp[t] ≥ 0` — імпорт/експорт з мережі, кВт·год
- `peak` — максимальний імпорт на горизонті (для peak shaving)

### 9.2. Цільова функція (мінімізувати)
```
Σ_t [ price_buy[t]·g_imp[t] − price_sell[t]·g_exp[t] + c_deg·(p_ch[t] + p_dis[t]) ]
  + w_peak · c_peak · peak
  + w_reserve · Σ_t max(0, soc_reserve − soc[t])   (лінеаризується slack-змінною)
```
де `c_deg = capex / (2 · cycle_life · capacity)` грн/кВт·год пропускної енергії.

### 9.3. Обмеження
```
soc[t] = soc[t−1] + η_ch·p_ch[t]·Δt − p_dis[t]·Δt/η_dis − self_discharge
soc_min ≤ soc[t] ≤ soc_max
soc[0] = поточний SoC з телеметрії;  soc[T] ≥ soc_end_target (за замовч. = soc[0])
p_ch[t] ≤ P_max · z[t];   p_dis[t] ≤ P_max · (1 − z[t])
g_imp[t] − g_exp[t] = load[t] + p_ch[t]·Δt − p_dis[t]·Δt − pv[t]
g_imp[t] ≤ peak;   peak ≤ peak_limit_kw·Δt (якщо PEAK_SHAVING жорсткий)
g_exp[t] ≤ export_limit_kwh (0, якщо експорт заборонений договором)
```
Стратегії з 6.7 — це просто набір вагів `w_*` і жорстких/м'яких обмежень.

### 9.4. Вихід
Список по годинах + метрики: очікуваний прибуток, кількість еквівалентних циклів, SoC-траєкторія. Час розв'язку має бути < 2 с для T=48.

### 9.5. Perfect-foresight режим
Той самий оптимізатор з фактичними цінами — верхня межа, відносно якої оцінюється якість ML.

## 10. Веб-застосунок

React 18 + TypeScript + Vite, Tailwind, стан — Zustand, графіки — ECharts (або Recharts), анімації — Framer Motion + власний SVG. Мова інтерфейсу — українська (i18n-готовність, ключі в JSON).

### 10.1. Сторінки

**1. Dashboard (головна) — realtime**
Головний елемент — **анімована SVG-схема енергопотоків**:
```
   [Мережа ОЕС]  ══►  [Лічильник]  ══►  [Підприємство 340 кВт]
        ▲                  │
        ║ експорт          ▼
        ╚════════  [EMS]  ◄══►  [BESS ▮▮▮▮▮▮▯▯▯▯ 63 %]
                    (мозок)         ▲ 180 кВт розряд
                                    └─ [PV 45 кВт] (опц.)
```
Вимоги до схеми:
- Вузли: Мережа, Підприємство (навантаження), BESS, EMS, PV (якщо увімкнено). Кожен — картка з іконкою, поточним значенням у кВт і міні-статусом.
- **Стрілки-потоки**: анімовані «частинки/тире», що рухаються вздовж лінії в напрямку потоку; швидкість і товщина пропорційні потужності; колір: зелений — розряд батареї/PV, помаранчевий — заряд з мережі, червоний — імпорт у дорогу годину, сірий — нуль. Напрямок стрілки змінюється при зміні знака потужності з плавною анімацією.
- **Батарея**: контейнер, який заповнюється рідиною (хвиля) до рівня SoC, колір за станом (зелений/жовтий/червоний біля меж), пульсація при заряді/розряді, іконка блискавки, температура, SoH.
- **EMS-вузол**: показує поточне рішення і його `reason` («Розряд: пік ціни 6 850 грн/МВт·год, план sch_…»), індикатор «думає» під час оптимізації.
- **Лічильник грошей** («Заощаджено/зароблено сьогодні: +12 430 грн») з анімацією зміни цифр.
- Панель годинника симуляції: сим-дата/час, швидкість (кнопки ‖ ▶ 1x 60x 600x 3600x, крок), поточна ціна РДН і ціна купівлі/продажу з підсвіткою рівня (дешево/середньо/пік).
- Нижче — графіки в реальному часі (останні 24–48 сим-годин): (а) ціна РДН факт + прогноз p10/p90; (б) навантаження, імпорт, потужність BESS (стовпчики +/−); (в) SoC план vs факт; (г) таймлайн графіка (Gantt-стрічка: заряд/розряд/idle по годинах, поточна година підсвічена).
- Стрічка подій (alarm, ре-оптимізація, FAULT, публікація РДН).

**2. Налаштування**
Вкладки: Батарея (усі параметри з 5.1), Ринок (тарифи, коеф. продажу, price caps, дозвіл експорту, peak_limit), Стратегія (вибір та ваги, reserve), Симуляція (сценарій, seed, швидкість, несправності), EMS (soc_tolerance, горизонт, крок, час прогнозу/оптимізації). Збереження → застосування без перезапуску (де можливо), інакше — кнопка «Перезапустити симуляцію».

**3. Дані**
Імпорт CSV (drag&drop, попередній перегляд, валідація), генерація синтетики з параметрами, перегляд рядів (графік з зумом), статистика (середня ціна за годину/місяць, heatmap «година × день тижня»).

**4. ML**
Список моделей і метрик, кнопка «Навчити» з формою параметрів і прогрес-баром, графік прогноз vs факт, backtest прибутку, активація моделі.

**5. Звіти**
Період → таблиця та графіки: витрати без BESS vs з BESS, дохід від експорту, вартість деградації, чистий ефект, кількість циклів, окупність (років). Експорт у CSV/XLSX. Порівняння стратегій (запустити ту саму добу з різними стратегіями → таблиця).

**6. Логи / Диспетчер**
Таблиця `dispatch_log` з фільтрами, перегляд конкретного графіка `schedules`.

## 15. Критерії приймання (сумарно)

1. Незалежні процеси BESS і EMS взаємодіють лише через MQTT; зупинка BESS-контейнера → EMS входить у SAFE_MODE і показує аларм.
2. На дашборді в реальному часі анімовані потоки: напрямок і товщина стрілок відповідають фактичній телеметрії; батарея візуально заповнюється/спорожнюється.
3. Для тестового періоду (1 місяць синтетики, seed=42) система показує: витрати без BESS, з BESS, чистий ефект, циклів — і `MILP+LightGBM` дає результат ближчий до perfect foresight, ніж `TOU_SIMPLE`.
4. Мінімум три ML-моделі порівняно на walk-forward, метрики видно в UI.
5. Усі параметри батареї, ринку, стратегії змінюються з UI; зміна ємності батареї одразу відбивається у наступній оптимізації.
6. Симуляція детермінована при заданому seed.
7. `docker compose up` з чистого клону — робоча система за ≤ 5 хв.
